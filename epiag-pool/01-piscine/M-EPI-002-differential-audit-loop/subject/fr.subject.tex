\chapter{Avant-propos}

La boucle d'audit différentiel tient en trois gestes :

\begin{enumerate}
  \item \textbf{Extraire} : quelles lignes le correctif ajoute-t-il, et dans
        quelle fonction ?
  \item \textbf{Paralléliser} : quelles fonctions, dans le même fichier ou
        le même sous-système, font un travail analogue sans avoir reçu le
        même test ?
  \item \textbf{Vérifier} : la symétrie supposée est-elle vraie, ou le
        chemin voisin est-il protégé par un autre invariant ?
\end{enumerate}

Le piège de l'étape 2 est de confondre \emph{ressemblance} et
\emph{équivalence}. Deux fonctions peuvent avoir le même nom, la même forme
et des invariants différents. L'étape 3 existe pour éliminer ces faux
positifs.

\begin{info}
Le papier utilise \texttt{grep} et, quand il est disponible, \texttt{ctags}.
\texttt{ctags} n'est pas obligatoire : \texttt{grep -RIn} suffit pour cette
piscine. L'important est de formuler une requête et de pouvoir la refaire.
Un outil plus puissant ne remplace pas l'hypothèse.
\end{info}

\chapter{Exercise 00}
\extitle{Extraire le code ajouté}
\turnindir{ex00}
\exnumber{00}
\exfiles{added-lines.md extraction.sh}
\exauthorize{git, grep, awk, un éditeur de texte}
\makeheaderfiles

Choisissez un correctif public de moins de cinquante lignes. Récupérez le
commit en local, puis extrayez uniquement les lignes ajoutées.

\begin{console}
git clone --filter=blob:none https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git linux
cd linux
git show <commit> -- <fichier> > /tmp/patch.diff
grep '^+' /tmp/patch.diff | grep -v '^+++' > /tmp/added.txt
\end{console}

\subsection*{Mission}

Dans \texttt{added-lines.md}, présentez :

\begin{enumerate}
  \item le commit, le fichier et la fonction ;
  \item les lignes ajoutées, classées en trois catégories : test, action,
        commentaire ;
  \item la ligne qui porte l'hypothèse principale ;
  \item une commande \texttt{grep} qui trouve les autres occurrences du
        motif ajouté.
\end{enumerate}

Écrivez \texttt{extraction.sh} de façon à ce qu'il prenne le commit et le
fichier en arguments, et qu'il produise les mêmes trois catégories.

\hint{Ne filtrez pas seulement les lignes qui contiennent \texttt{if}. Un
correctif peut ajouter une affectation, un appel de fonction, ou déplacer
une vérification.}

\chapter{Exercise 01}
\extitle{Trouver les twins avec grep}
\turnindir{ex01}
\exnumber{01}
\exfiles{twins.md}
\exauthorize{grep, find, un éditeur de texte}
\makeheaderfiles

Les « twins » sont les fonctions qui font un travail analogue dans un autre
chemin. Elles ne sont pas nécessairement des copies.

\subsection*{Préparer la recherche}

\begin{console}
grep -RIn --include='*.c' 'nft_setelem' linux/net/netfilter > /tmp/nft-hits.txt
grep -i 'catchall' /tmp/nft-hits.txt
\end{console}

Si \texttt{ctags} est installé, vous pouvez aussi créer un index
(\texttt{ctags -R --c-kinds=f --fields=+n linux/net/netfilter}). Ce n'est
pas exigé : la commande \texttt{grep} ci-dessus donne déjà les fichiers et
les lignes.

\subsection*{Mission}

Dans \texttt{twins.md}, listez au moins cinq fonctions candidates autour de
la fonction corrigée. Pour chacune :

\begin{enumerate}
  \item son nom, son fichier et sa ligne ;
  \item la raison pour laquelle elle ressemble à la fonction corrigée ;
  \item l'invariant qu'elle devrait partager ;
  \item le test qui manque, s'il manque ;
  \item le statut : \emph{candidat sérieux}, \emph{faux positif}, ou
        \emph{à vérifier}.
\end{enumerate}

Justifiez chaque statut avec une commande ou un extrait de code. Un twin
n'est pas coupable parce qu'il ressemble ; il est suspect parce qu'il
partage un invariant non vérifié.

\chapter{Exercise 02}
\extitle{Vérifier la symétrie}
\turnindir{ex02}
\exnumber{02}
\exfiles{symmetry-check.md}
\exauthorize{git, grep, un éditeur de texte}
\makeheaderfiles

Voici un extrait simplifié du modèle de génération nf\_tables. Deux
fonctions vérifient l'état d'un élément avant de le désactiver.

\begin{console}
static bool nft_setelem_active(const struct nft_set *set,
                               const struct nft_set_elem *elem)
{
    return nft_is_active(set->net, elem);
}

static bool nft_setelem_active_next(const struct nft_set *set,
                                    const struct nft_set_elem *elem)
{
    return nft_is_active_next(set->net, elem);
}
\end{console}

\subsection*{Mission}

Dans \texttt{symmetry-check.md} :

\begin{enumerate}
  \item Expliquez la différence entre les deux fonctions.
  \item Pour chaque appelant, indiquez s'il est dans un chemin de
        transaction ou dans un chemin de nettoyage.
  \item Identifiez l'appelant qui devrait utiliser la version
        \texttt{\_next} mais utilise la version courante.
  \item Proposez un test de symétrie qui échoue avant le correctif et passe
        après, sans exécuter d'exploit.
\end{enumerate}

\begin{warn}
Un test de symétrie n'est pas un test de sécurité complet. Il vérifie
seulement qu'une hypothèse locale est cohérente entre deux chemins.
\end{warn}

\chapter{Exercise 03}
\extitle{Triage de dix candidats}
\turnindir{ex03}

\exfiles{triage.md}
\exauthorize{un éditeur de texte, les règles du dépôt compagnon}
\makeheaderfiles

Prenez les dix candidats produits par les exercices précédents, ou les
candidats fournis par votre formateur. Appliquez la grille de triage du
papier :

\begin{center}
\begin{tabularx}{\linewidth}{|l|X|c|}
\hline
\textbf{Critère} & \textbf{Question} & \textbf{Points} \\ \hline
Confiance & Le correctif est-il réellement lié au candidat ? & 0--3 \\ \hline
Proximité & Le candidat est-il dans le même chemin ou un twin direct ? & 0--3 \\ \hline
Impact & Que se passe-t-il si l'hypothèse est fausse ? & 0--2 \\ \hline
Testabilit\'e & Peut-on vérifier sans exploit ni cible réelle ? & 0--2 \\ \hline
\end{tabularx}
\end{center}

Dans \texttt{triage.md}, donnez pour chaque candidat : score total,
justification en trois lignes, et action (\emph{ignorer},
\emph{investiguer}, \emph{prioriser}). Rappelez la règle : score
\texttt{>= 6} = investiguer, score \texttt{>= 8} = prioriser.
