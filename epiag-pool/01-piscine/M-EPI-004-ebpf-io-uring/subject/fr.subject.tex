\chapter{Avant-propos}

eBPF et io\_uring échouent de deux manières différentes.

\begin{center}
\begin{tabularx}{\linewidth}{|p{0.2\linewidth}|X|X|}
\hline
\textbf{Composant} & \textbf{Forme} & \textbf{Question d'audit} \\ \hline
Vérificateur eBPF & Predictive Oracle : il analyse un programme avant de
l'exécuter. & Quelle propriété le vérificateur croit-il avoir prouvée, et
quelle transformation du JIT ou du contexte peut l'invalider ? \\ \hline
io\_uring & Concurrent Proxy : il partage des rings et des buffers entre
utilisateur et noyau. & À quel moment la ressource est-elle validée, et à
quel moment est-elle utilisée ou libérée ? \\ \hline
\end{tabularx}
\end{center}

Le réflexe eBPF est donc : \emph{suivre l'état abstrait}. Le réflexe
io\_uring est : \emph{suivre le cycle de vie et la synchronisation}.

\begin{info}
Le papier montre que les correctifs eBPF se concentrent souvent sur une
passe du vérificateur, tandis que le bug réel vient d'une interaction entre
deux passes, ou entre le vérificateur et le JIT. C'est le propre d'un
oracle : il peut être localement correct et globalement faux.
\end{info}

\chapter{Exercise 00}
\extitle{Carte du vérificateur}
\turnindir{ex00}
\exnumber{00}
\exfiles{verifier-map.md}
\exauthorize{grep, un éditeur de texte}
\makeheaderfiles

Dans \texttt{verifier-map.md}, décrivez le pipeline minimal d'un programme
eBPF :

\begin{enumerate}
  \item chargement et vérification des instructions ;
  \item suivi des types de registres ;
  \item suivi des bornes scalaires ;
  \item vérification des accès mémoire ;
  \item conversion vers le JIT.
\end{enumerate}

Pour chaque étape, indiquez :

\begin{itemize}
  \item la structure de données principale ;
  \item la fonction d'entrée ;
  \item une propriété que l'étape \emph{croit} garantir ;
  \item un endroit où cette propriété pourrait être perdue.
\end{itemize}

\hint{Le vérificateur ne prouve pas « ce programme est sûr ». Il prouve un
ensemble de propriétés locales sur un modèle abstrait. Votre carte doit
montrer les coutures entre ces propriétés.}

\chapter{Exercise 01}
\extitle{ALU32 et bornes 64-bit}
\turnindir{ex01}
\exnumber{01}
\exfiles{alu32.md}
\exauthorize{git, grep, un éditeur de texte}
\makeheaderfiles

CVE-2020-27194 puis CVE-2021-3490 concernent le suivi des bornes après des
opérations 32 bits. Le premier correctif ne ferme pas toute la classe : le
second est un variant du même modèle.

\subsection*{Mission}

Dans \texttt{alu32.md} :

\begin{enumerate}
  \item Expliquez pourquoi une opération 32 bits peut produire une valeur
        dont les 32 bits de poids fort ne sont pas ceux attendus.
  \item Décrivez ce que le vérificateur stocke dans
        \texttt{scalar32\_min\_max\_or()} et
        \texttt{scalar32\_min\_max\_and()}.
  \item Pourquoi le correctif de CVE-2020-27194 est-il incomplet ?
  \item Quelle question d'audit le correctif de CVE-2021-3490 aurait-il dû
        déclencher dans la revue du premier patch ?
\end{enumerate}

\subsection*{Sources}
\begin{itemize}
  \item NVD : \url{https://nvd.nist.gov/vuln/detail/CVE-2020-27194}
  \item NVD : \url{https://nvd.nist.gov/vuln/detail/CVE-2021-3490}
  \item Analyse de Manfred Paul, Pwn2Own 2021.
\end{itemize}

\chapter{Exercise 02}
\extitle{OR\_NULL et pruning}
\turnindir{ex02}
\exnumber{02}
\exfiles{oracle.md}
\exauthorize{git, grep, un éditeur de texte}
\makeheaderfiles

Deux CVE illustrent deux manières de tromper l'oracle :

\begin{itemize}
  \item CVE-2022-23222 : un registre de type \texttt{OR\_NULL} est traité
        comme un pointeur valide dans certaines opérations arithmétiques.
  \item CVE-2023-2163 : la passe de pruning élimine un état jugé redondant
        alors qu'il porte une contrainte nécessaire.
\end{itemize}

\subsection*{Mission}

Dans \texttt{oracle.md}, répondez :

\begin{enumerate}
  \item Quelle est la différence entre « le vérificateur accepte le
        programme » et « le programme ne peut pas violer la propriété » ?
  \item Pour CVE-2022-23222, quel type de registre est mal propagé, et
        quelle opération transforme ce type en pointeur utilisable ?
  \item Pour CVE-2023-2163, pourquoi le pruning est-il à la fois une
        optimisation nécessaire et une source de bugs ?
  \item Proposez une requête \texttt{grep} qui trouve les endroits où un
        état est marqué comme équivalent à un état déjà visité.
\end{enumerate}

\begin{warn}
Ne cherchez pas à charger un programme qui déclenche ces bugs. Le but est
de comprendre pourquoi une preuve locale ne compose pas toujours avec les
autres passes.
\end{warn}

\chapter{Exercise 03}
\extitle{io\_uring : rings et durée de vie}
\turnindir{ex03}
\exnumber{03}
\exfiles{io-uring.md}
\exauthorize{grep, un éditeur de texte}
\makeheaderfiles

io\_uring partage des Submission Queue Entries, des Completion Queue
Entries et parfois des buffers enregistrés. Le noyau et l'utilisateur
avancent des têtes et des queues séparément.

\subsection*{Mission}

Dans \texttt{io-uring.md} :

\begin{enumerate}
  \item Dessinez le cycle de vie d'une requête : soumission, exécution,
        complétion, libération.
  \item Identifiez les ressources partagées et leurs règles de
        synchronisation.
  \item Expliquez pourquoi une validation faite à la soumission peut être
        invalide au moment de l'exécution.
  \item Pour CVE-2023-2598 et CVE-2024-0582, indiquez la ressource dont la
        durée de vie est mal protégée, sans écrire d'exploit.
  \item Donnez trois questions d'audit pour un prochain patch io\_uring.
  \item Expliquez pourquoi un test de course doit contrôler l'ordre des
        accès mémoire, et pourquoi ajouter un \texttt{sleep()} ne prouve
        rien.
\end{enumerate}

\subsection*{Sources}
\begin{itemize}
  \item NVD : \url{https://nvd.nist.gov/vuln/detail/CVE-2023-2598}
  \item NVD : \url{https://nvd.nist.gov/vuln/detail/CVE-2024-0582}
  \item Documentation io\_uring :
        \url{https://kernel.dk/io_uring.pdf}
\end{itemize}

\chapter{Exercise 04}
\extitle{Mesurer le patch gap}
\turnindir{ex04}
\exnumber{04}
\exfiles{patch-gap.md patch-gap.sh}
\exauthorize{git, python3, un éditeur de texte}
\makeheaderfiles

Le \emph{patch gap} est le temps entre la publication d'un correctif amont
et son application dans une branche stable ou une distribution.

\subsection*{Mission}

Choisissez cinq CVE parmi celles du module. Pour chacune, trouvez :

\begin{enumerate}
  \item la date du commit amont ;
  \item la date d'entrée dans la branche stable que vous suivez ;
  \item la date de publication de l'avis de sécurité ;
  \item le nombre de jours entre le commit amont et la branche stable.
\end{enumerate}

Écrivez \texttt{patch-gap.sh} qui prend une liste de commits et produit un
tableau CSV avec les dates et les écarts. Le script ne doit pas cloner tout
le noyau : utilisez \texttt{git log -1} sur un dépôt existant.

Dans \texttt{patch-gap.md}, concluez sur la différence entre \emph{temps de
correction} et \emph{temps d'exposition}.
