\chapter{Avant-propos}

Un vérificateur eBPF est un oracle : il promet qu'un programme respecte
certaines propriétés avant de l'exécuter. Un oracle peut être :

\begin{itemize}
  \item \textbf{localement correct} : chaque passe fait ce qu'elle dit ;
  \item \textbf{globalement faux} : la composition des passes ne préserve
        pas la propriété.
\end{itemize}

io\_uring est un proxy concurrent : il ne promet pas que la ressource est
valide, il organise son accès. Le bug apparaît quand la validation et
l'utilisation ne sont pas dans la même fenêtre de synchronisation.

\chapter{Exercise 00}
\extitle{Modèle d'état du vérificateur}
\turnindir{ex00}
\exnumber{00}
\exfiles{verifier-state.md}
\exauthorize{grep, ctags, un éditeur de texte}
\makeheaderfiles

Dans \texttt{verifier-state.md}, modélisez l'état d'un registre eBPF :

\begin{enumerate}
  \item type (scalaire, pointeur, \texttt{OR\_NULL}, etc.) ;
  \item bornes minimales et maximales ;
  \item précision 32/64 bits ;
  \item provenance (stack, map, contexte, appel de helper) ;
  \item contraintes de lecture et d'écriture.
\end{enumerate}

Pour chaque champ, indiquez la fonction qui le met à jour et une passe qui
peut l'invalider.

\hint{Le vérificateur ne suit pas une valeur réelle : il suit un ensemble
d'états possibles. Une erreur de précision n'est pas une erreur de valeur,
c'est une erreur sur l'ensemble.}

\chapter{Exercise 01}
\extitle{ALU32, bornes et variantes}
\turnindir{ex01}
\exnumber{01}
\exfiles{alu32-variants.md}
\exauthorize{git, grep, un éditeur de texte}
\makeheaderfiles

Étudiez la chaîne CVE-2020-27194 vers CVE-2021-3490. Le second correctif
montre que le premier n'avait pas fermé la classe.

\subsection*{Mission}

Dans \texttt{alu32-variants.md} :

\begin{enumerate}
  \item expliquez la différence entre une opération 32 bits et une
        opération 64 bits sur le même registre ;
  \item montrez comment les bornes 32 bits sont utilisées pour déduire une
        borne 64 bits ;
  \item identifiez l'hypothèse qui manque dans le premier correctif ;
  \item écrivez une requête \texttt{grep} qui trouve les fonctions de mise
        à jour des bornes ;
  \item proposez un test de non-régression qui vérifie l'invariant, sans
        charger de programme dangereux.
\end{enumerate}

\chapter{Exercise 02}
\extitle{Pruning et JIT}
\turnindir{ex02}
\exnumber{02}
\exfiles{pruning-jit.md}
\exauthorize{git, grep, objdump, un éditeur de texte}
\makeheaderfiles

Le pruning supprime des états jugés équivalents. CVE-2023-2163 montre
qu'une équivalence locale peut être fausse globalement.

\subsection*{Mission}

Dans \texttt{pruning-jit.md} :

\begin{enumerate}
  \item décrivez la structure qui stocke les états visités ;
  \item expliquez le critère d'équivalence utilisé par le pruning ;
  \item donnez un exemple abstrait où deux états sont équivalents pour une
        passe mais pas pour une autre ;
  \item comparez la sémantique du vérificateur et celle du JIT sur une
        opération arithmétique ;
  \item listez trois endroits où le JIT peut introduire une différence
        (extension de signe, division, décalage).
\end{enumerate}

\chapter{Exercise 03}
\extitle{io\_uring : PBUF et durée de vie}
\turnindir{ex03}
\exnumber{03}
\exfiles{pbuf.md}
\exauthorize{grep, ctags, un éditeur de texte}
\makeheaderfiles

Étudiez le cycle de vie d'un buffer enregistré et d'une requête io\_uring.
Les CVE-2023-2598 et CVE-2024-0582 touchent des ressources dont la durée de
vie est mal protégée.

\subsection*{Mission}

Dans \texttt{pbuf.md} :

\begin{enumerate}
  \item décrivez les rings SQ/CQ et les buffers enregistrés ;
  \item identifiez les points de validation et les points de libération ;
  \item expliquez pourquoi la validation à la soumission ne suffit pas ;
  \item proposez un modèle de propriété (« qui possède la ressource, quand
        la rend-elle ? ») ;
  \item listez cinq questions d'audit pour un patch io\_uring ;
  \item expliquez pourquoi un test de course doit contrôler l'ordonnancement
        (communication points, injection de délai) plutôt que d'ajouter un
        \texttt{sleep()}.
\end{enumerate}

\begin{warn}
Les bugs de concurrence sont sensibles au timing. Une analyse statique peut
donner une fausse impression de certitude. Indiquez toujours les fenêtres
que vous n'avez pas prouvées. Le projet MAccConc de Project Zero montre
qu'un test de course reproductible repose sur des accès mémoire observés et
un ordre imposé, pas sur une attente arbitraire.
\end{warn}

\chapter{Exercise 04}
\extitle{Patch gap et backport}
\turnindir{ex04}
\exnumber{04}
\exfiles{backport.md}
\exauthorize{git, python3, un éditeur de texte}
\makeheaderfiles

Choisissez trois CVE eBPF et deux CVE io\_uring. Pour chacune, comparez le
correctif amont et le backport dans une branche stable.

\subsection*{Mission}

Dans \texttt{backport.md} :

\begin{enumerate}
  \item listez les commits amont et stable ;
  \item identifiez les différences de contexte ;
  \item expliquez pourquoi un backport peut être incomplet ;
  \item mesurez le délai entre amont et stable ;
  \item comparez votre délai avec le patch gap OtterRoot
        (CVE-2024-26809) : commit public, publication de l'exploit
        KernelCTF, puis arrivée dans Ubuntu et Debian ;
  \item concluez sur le risque d'exposition.
\end{enumerate}
