\chapter{Avant-propos}

Un patch diff est une fenêtre sur la root cause. Le message de commit dit
ce que le développeur \emph{croit} avoir corrigé ; le diff montre ce qu'il
a \emph{effectivement} changé ; le binaire montre ce que le compilateur a
\emph{réellement} produit.

Les trois récits ne coïncident pas toujours. Votre travail est de les
confronter, pas de choisir le plus confortable.

\begin{info}
Le patch diffing ne remplace pas la lecture du code. Il sert à repérer les
changements de contrôle, les constantes, les bornes et les appels qui
n'apparaissent pas dans le message de commit.
\end{info}

\chapter{Exercise 00}
\extitle{Archéologie de commit}
\turnindir{ex00}
\exnumber{00}
\exfiles{commit-archaeology.md}
\exauthorize{git, grep, un éditeur de texte}
\makeheaderfiles

Choisissez CVE-2023-4244 et CVE-2024-1085. Retrouvez leurs commits de
correction et replacez-les dans l'historique du fichier.

\subsection*{Mission}

Dans \texttt{commit-archaeology.md} :

\begin{enumerate}
  \item listez les commits, leurs dates, leurs auteurs et leurs messages ;
  \item identifiez les commits qui ont introduit ou retiré la garde
        concernée ;
  \item construisez une chronologie de trois lignes ;
  \item expliquez pourquoi le second correctif n'est pas une simple
        duplication du premier.
\end{enumerate}

\begin{console}
git log --oneline --decorate -- net/netfilter/nf_tables_api.c | head -40
git show --stat <commit>
git blame -L <debut>,<fin> net/netfilter/nf_tables_api.c
\end{console}

\chapter{Exercise 01}
\extitle{Du diff à la root cause}
\turnindir{ex01}
\exnumber{01}
\exfiles{root-cause.md}
\exauthorize{git, grep, ctags, un éditeur de texte}
\makeheaderfiles

Prenez CVE-2023-35001. Le correctif modifie la manière dont un champ de
registre est lu dans \texttt{nft\_byteorder\_eval()}.

\subsection*{Mission}

Dans \texttt{root-cause.md} :

\begin{enumerate}
  \item décrivez la structure de données et la disposition mémoire des
        champs concernés ;
  \item montrez comment une valeur d'entrée atteint l'accès hors limites ;
  \item distinguez la \emph{root cause} de la \emph{condition
        d'exploitation} ;
  \item expliquez pourquoi le correctif ne protège pas les autres
        opérations qui manipulent des registres ;
  \item proposez une requête \texttt{grep} qui trouve les opérations
        analogues.
\end{enumerate}

\hint{La root cause est souvent une hypothèse de type ou de taille. La
condition d'exploitation est souvent un chemin d'appel et un état de
registre. Ne mélangez pas les deux.}

\chapter{Exercise 02}
\extitle{Diff binaire}
\turnindir{ex02}
\exnumber{02}
\exfiles{bindiff.md}
\exauthorize{objdump, radiff2, Diaphora ou BinDiff, un éditeur de texte}
\makeheaderfiles

Comparez deux versions publiques d'un binaire contenant la fonction
corrigée. Si vous n'avez pas Diaphora ou BinDiff, utilisez
\texttt{objdump -d} et \texttt{radiff2}.

\subsection*{Mission}

Dans \texttt{bindiff.md} :

\begin{enumerate}
  \item identifiez la fonction dans les deux binaires ;
  \item comparez les blocs de base et les sauts conditionnels ;
  \item repérez la constante, la borne ou l'appel ajouté ;
  \item expliquez ce que le diff binaire montre que le diff source ne
        montre pas ;
  \item listez les limites de votre analyse (optimisation, inlining,
        stripping).
\end{enumerate}

\begin{warn}
Ne diffusez pas de binaire propriétaire. Utilisez uniquement des binaires
que vous avez le droit d'analyser.
\end{warn}

\chapter{Exercise 03}
\extitle{Mesurer le patch gap}
\turnindir{ex03}
\exnumber{03}
\exfiles{patch-gap.md patch-gap.py}
\exauthorize{git, python3, un éditeur de texte}
\makeheaderfiles

Choisissez cinq CVE du papier. Pour chacune, mesurez :

\begin{itemize}
  \item la date du commit amont ;
  \item la date d'arrivée dans la branche stable ;
  \item la date de publication de l'avis ;
  \item la date de disponibilité du correctif dans une distribution.
\end{itemize}

Écrivez \texttt{patch-gap.py} qui prend un fichier CSV de commits et
produit un tableau avec les écarts en jours. Le script doit gérer les
fuseaux horaires et les dates manquantes.

Dans \texttt{patch-gap.md}, distinguez :

\begin{enumerate}
  \item le temps de correction (commit amont) ;
  \item le temps de backport (branche stable) ;
  \item le temps d'activation (redémarrage, bascule de flag) ;
  \item le temps d'exposition (systèmes non patchés).
\end{enumerate}

Classez ensuite les mécanismes d'urgence décrits par Project Zero
(feature flags, filtering, dual stack) et expliquez pourquoi ils réduisent
l'exposition sans fermer la root cause.

\chapter{Exercise 04}
\extitle{Écrire un finding}
\turnindir{ex04}
\exnumber{04}
\exfiles{finding.md}
\exauthorize{un éditeur de texte}
\makeheaderfiles

Rédigez un finding de deux pages maximum sur le candidat le plus solide de
vos exercices précédents. Le finding doit être compréhensible par un
ingénieur sécurité qui ne connaît pas le sous-système.

Structure imposée :

\begin{enumerate}
  \item \textbf{Titre} : composant, fonction, type de faiblesse.
  \item \textbf{Résumé} : trois phrases.
  \item \textbf{Contexte} : version, commit, configuration.
  \item \textbf{Root cause} : mécanisme précis.
  \item \textbf{Preuve} : extraits de code, commandes, diff.
  \item \textbf{Impact} : ce qui est atteignable, et ce qui ne l'est pas.
  \item \textbf{Remédiation} : correctif proposé ou question à poser.
  \item \textbf{Atténuation d'urgence} : ce qui réduit l'exposition sans
        fermer la root cause.
  \item \textbf{Limites} : ce que vous n'avez pas vérifié.
\end{enumerate}

Un finding n'est pas un article de blog : pas de storytelling, pas de
conclusion triomphale. Des faits, des preuves, des limites.
